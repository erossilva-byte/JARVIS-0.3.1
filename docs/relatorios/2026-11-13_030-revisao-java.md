# Ajuste 030 — revisão de compilação e ciclo de vida do Java da Fase 4B

Data: 2026-11-13
Branch: `work/1.48.0-fase2-consolidacao`

## Por que este ajuste

Antes de gastar uma rodada de CI, os arquivos Java alterados nas últimas fases foram lidos por
inteiro com foco em duas coisas: o que não compila e o que compila mas se comporta mal no ciclo
de vida do serviço. A revisão achou um defeito grave que os testes não pegavam, porque testavam
a forma do código, não a API do Android.

## O que foi corrigido

1. **Microfone ocupado nunca era detectado.** `getClientPackageName()` devolve vazio sem a
   permissão de sistema `MODIFY_AUDIO_ROUTING` (documentação do AOSP). A detecção agora compara
   a **sessão de áudio** do nosso `AudioRecord` (`getClientAudioSessionId()`, API pública) e conta
   as gravações restantes; o nome do pacote só aparece se o Android entregar.
2. **Fone sobrescrevia pausa manual**: `pausarPorFone()` agora respeita `pausadoManual`.
3. **Teste anunciava "diga Jarvis" com o microfone bloqueado**: a mensagem passou para o
   `onState` e só aparece com captura confirmada.
4. **`Result.retry()` sem limite**: no máximo duas tentativas por ciclo no Worker.
5. `kwsEngine` virou `volatile`, porque a sessão de áudio é lida também pela ponte (outra thread).

## Evidência

| Verificação | Resultado |
|---|---|
| `node tests/test_microfone.js` | 12 verificações aprovadas (inclui sessão de áudio e `sessaoAudio()` no motor) |
| `npm run test:all` | **exit 0** |
| `python3 ci/preflight_android.py` | exit 0 — 23 classes, 6 workflows |
| Documentação da API | AOSP: pacote vazio sem `MODIFY_AUDIO_ROUTING` |
| Revisão escrita | `docs/REVISAO-JAVA-COMPILACAO.md` |

## O que a revisão NÃO prova

Nada foi compilado (sem SDK) e nada foi medido no aparelho. Os pontos que dependem do CI e do
Poco X7 estão listados como riscos na revisão e como medições no aceite da fase: entrega do
broadcast de fone com receiver não-exportado, lista de gravações em HyperOS e inicialização do
WorkManager no APK final.

## Correções de documentação

Os relatórios 026 e 027 afirmavam que a detecção informava o **pacote** do outro app. Isso não
vale para app comum; os dois receberam nota de correção apontando para este ajuste.
