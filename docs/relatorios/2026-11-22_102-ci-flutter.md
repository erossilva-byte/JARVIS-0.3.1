# Relatório 102 — a esteira de CI passa a ser a do Flutter

Versão 1.88.0+18800. Data: 2026-11-22.

## O que estava acontecendo

O commit de integração na `main` (`a16aa795`) disparou duas esteiras e as duas
deram problema:

- `ci-android-auditoria.yml` — os 14 primeiros passos passaram (Java, SDK 36,
  `npm install`, cópia dos módulos para `www/`, `npx cap add android`, patches de
  manifesto/gradle/identidade). Falhou no passo "Testes estáticos e regressão"
  (`npm run test:all`), e "Compilar APK debug" e "Publicar APK e checksum"
  ficaram pulados.
- `build-apk.yml` — cancelada em 1 segundo, sem nenhum passo e sem runner. As
  duas declaram o **mesmo** grupo de concorrência
  (`jarvis-nova-android-${{ github.ref }}`) com `cancel-in-progress: true`:
  quem começa derruba a outra na fila.

O problema de fundo não era o código: as duas esteiras são da era JS/Capacitor —
copiam `app.js` e companhia para `www/` e montam o APK daquele projeto —, e a
`main` hoje é Flutter. A esteira que testa a linha Flutter
(`flutter-native.yml`) não observa a `main`, então a `main` nascia vermelha sem
que nenhum teste do app tivesse rodado.

## O que mudou

**Novo — `.github/workflows/flutter-ci.yml`**, disparado em push e pull request
na `main` (e manualmente):

1. `actions/checkout@v4`;
2. `subosito/flutter-action@v2` com canal estável e cache;
3. `flutter pub get`;
4. `flutter analyze`;
5. `flutter test`;
6. `python3 ci/contratos_python.py`.

**Novo — `ci/contratos_python.py`**: roda os contratos Python na mesma ordem do
`npm run test:all`, lendo a lista do `package.json` em vez de manter uma cópia.
Cada comando vira um grupo no log; no fim, diz quantos passaram e lista os que
falharam. `--lista` mostra a lista sem executar.

**Aposentadas — `build-apk.yml` e `ci-android-auditoria.yml`**: continuam no
repositório (contratos históricos leem o conteúdo delas), mas o gatilho é só
`workflow_dispatch`. Não disparam mais em push nem em pull request.

**Concorrência**: `legado-build-apk-…`, `legado-auditoria-android-…` e
`flutter-ci-…` — um grupo por workflow. O contrato novo reprova grupo repetido
em qualquer workflow do repositório, então o acidente não volta por descuido.

**Novo contrato — `tests/test_ci_flutter.py`**: prende a esteira nova
(gatilho na `main`, Flutter instalado, pub get → analyze → test → contratos,
nessa ordem), o modo manual das antigas, a unicidade dos grupos de concorrência
e a lista do runner igual à do `test:all`.

## O que foi verificado aqui

- `flutter analyze` — sem problemas.
- `flutter test` — toda a suíte Dart verde.
- `python3 ci/contratos_python.py` — todos os comandos Python do `test:all`
  passaram, incluindo o contrato 102.
- `python3 tests/test_ci_flutter.py` — aprovado isoladamente.

## Limite honesto

O workflow novo **não rodou no GitHub** nesta sessão: YAML de Actions não é
validado por teste local, e a primeira execução real — no push — é o teste de
verdade. Se algo escorregar lá, é na instalação do Flutter (canal estável) ou no
tempo do job, não nos comandos: eles são exatamente os que passaram aqui.
